# آپدیت آسان رابو

## کار روزمره پس از راه‌اندازی
۱. تغییرات را در Google AI Studio انجام بده و به مخزن GitHub ارسال کن.
۲. در GitHub قسمت Actions، اجرای «Rabo - Build and Publish» باید سبز شود.
۳. اگر انتشار خودکار فعال است، سایت خودکار آپدیت می‌شود؛ نتیجه job «auto-deploy» باید سبز باشد.
۴. اگر انتشار خودکار فعال نیست: در cPanel > Git Version Control > Manage > Pull or Deploy، ابتدا «Update from Remote» و بعد «Deploy HEAD Commit» را بزن.

ارسال کد به شاخه main انجام می‌شود. شاخه cpanel-release خروجی تولیدشده است؛ در آن دستی کد ننویس.
این مسیر فقط ظاهر و منطق مرورگر را منتشر می‌کند. تغییر PHP، دیتابیس یا خدمات Node با این مسیر منتشر نمی‌شود و باید جداگانه توسط مسئول فنی تطبیق داده شود.

## راه‌اندازی اولیه — فقط یک بار توسط مسئول فنی

۱. فایل‌های بسته راه‌اندازی را با حفظ مسیرها در ریشه مخزن قرار بده. کد React باید در پوشه rabo-automation-14050729-0.0.3 بماند. package-lock.json همراه بسته را هم ارسال کن.
۲. GitHub > Settings > Actions باید اجرای workflow را مجاز بداند؛ workflow برای تولید شاخه خروجی مجوز Contents write می‌خواهد. اگر قوانین سازمان/مخزن مانع نوشتن شاخه شد، فقط همین شاخه خروجی باید مجاز شود؛ حفاظت main را حذف نکن.
۳. workflow را اجرا کن و صبر کن شاخه cpanel-release ساخته شود.
۴. در cPanel > Domains، Document Root دقیق raboautomation.ir را بخوان. نام کاربری یا public_html را حدس نزن.
۵. در File Manager گزینه Show Hidden Files را فعال کن. بیرون ریشه سایت، در مسیر خانه کاربر پوشه .config بساز و فایل rabo-deploy.conf را داخلش قرار بده. محتوا فقط این باشد؛ مسیر را با مسیر واقعی عوض کن:

    RABO_WEBROOT='/home/CPANEL_USER/ACTUAL_DOCUMENT_ROOT'

۶. مجوز فایل تنظیمات را 600 قرار بده. PHP/DB config موجود سایت را جابه‌جا نکن.
۷. در Git Version Control مخزن GitHub را در یک پوشه جدا از ریشه سایت Clone کن، مثلاً /home/CPANEL_USER/repositories/rabo-release. اگر قبلاً مخزن موجود است، ابتدا تغییرات محلی و کاربرد آن بررسی شود؛ بی‌بررسی branch آن را عوض نکن.
۸. در Basic Information شاخه Checked-Out Branch را cpanel-release قرار بده. در Pull or Deploy دو دکمه آپدیت و انتشار را بزن.
۹. نتیجه موفق باید RABO UPDATE SUCCESS باشد. سپس سایت و rabo-version.json را باز کن و نسخه را بررسی کن. ورود و یک عملیات اصلی را با حساب مجاز آزمایش کن.
۱۰. این اسکریپت به Bash، flock و ابزارهای معمول لینوکس نیاز دارد؛ اگر هاست اجازه اجرای آن‌ها را ندهد، تنظیم Git deployment باید با پشتیبانی هاست تکمیل شود.

## انتشار کاملاً خودکار با SSH — اختیاری، یک بار
پس از موفقیت انتشار دستی، یک کلید SSH اختصاصی این سامانه بساز و public key را در cPanel مجاز کن. قبل از فعال‌سازی، مسیر مخزن و اثر دسترسی کلید بررسی شود. کلید اصلی شخصی را به GitHub نده.
در GitHub محیط production بساز و Secrets زیر را فقط آنجا ثبت کن:
- RABO_SSH_HOST: میزبان واقعی SSH
- RABO_SSH_PORT: پورت SSH، معمولاً 22
- RABO_SSH_USER: کاربر cPanel
- RABO_SSH_KEY: private key اختصاصی انتشار
- RABO_SSH_KNOWN_HOSTS: خط known_hosts که اثرانگشت آن با اطلاعات معتبر هاست تطبیق داده شده است؛ صرفاً خروجی تأییدنشده ssh-keyscan کافی نیست.
Repository Variables:
- RABO_REMOTE_REPO: مسیر کامل همان مخزن cPanel با شاخه cpanel-release، بدون فاصله
- RABO_AUTO_DEPLOY: مقدار true

از این پس ارسال کد به main، ساخت و انتشار را پشت سر هم انجام می‌دهد. اگر SSH موجود نیست، مسیر دو دکمه‌ای کافی است.
بسته ZIP بک‌اند، رمز یا کلید SSH ندارد. هیچ‌کدام را در GitHub یا AI Studio paste نکن.

## برگشت به نسخه قبل
در Terminal هاست، وارد پوشه مخزن cpanel-release شو و اجرا کن:

    /bin/bash deploy/install.sh rollback

این دستور فقط فایل‌های ظاهری نسخه قبل را برمی‌گرداند. اطلاعات جاری، API و دیتابیس را برنمی‌گرداند و تغییر نمی‌دهد.
قبل از هر انتشار/برگشت، snapshot فایل‌های ظاهری در ~/rabo-frontend-backups ساخته می‌شود. فایل‌های assets قدیمی خودکار حذف نمی‌شوند تا تب‌های باز و برگشت نسخه خراب نشوند. پس از چند انتشار، حجم این پوشه‌ها باید توسط مسئول فنی پایش شود.
اگر انتشار با خطای کپی/فضا قطع شد، آن را موفق حساب نکن. index در پایان جابه‌جا می‌شود، اما این روش تراکنش اتمیک کل سایت نیست؛ snapshot برای برگشت وجود دارد.

## محدوده حفاظت
اسکریپت فقط index.html، assets، fonts، لوگوها، manifest، sw.js و rabo-version.json را می‌نویسد. PHP، .htaccess، uploads، data، تنظیمات هاست و دیتابیس در بسته نیستند. هیچ SQL اجرا نمی‌شود. API ناسازگار باید پیش از انتشار رابط جدید در محیط تست بررسی شود.
صفحه ورود و یک عملیات واقعی باید پس از انتشار آزمون شود؛ سبزشدن Build به معنی سالم‌بودن بک‌اند نیست.
